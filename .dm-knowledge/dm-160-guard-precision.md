- **[invariant]** dm-command-guard.sh is STILL UNWIRED. Arming it (#89) was attempted and reverted in the same PR: the guard refused ordinary compound shell, and the runtime makes a hook a weak place to put a control. Wiring, when it happens, resolves the script from `DM_HOME` else by walking up from `$PWD` — NOT `git rev-parse --show-toplevel`, because a managed clone/worktree toplevel has no `bin/`. Editing `.claude/settings.json` changes a SHA frozen in `config/runtime-performance-baseline.json`, so the baseline moves in the same commit.  _(2026-07-25T00:00:00Z)_
- **[pitfall]** A `PreToolUse` hook FAILS OPEN. Measured on Claude Code 2.1.219: a command hook that sleeps past its `timeout` does not block — the tool runs. A control hook exiting 2 immediately does block, so the hook was live and the timeout is what let it through. Docs state this for `UserPromptSubmit` but NOT for `PreToolUse`. Any exit code other than 0 or 2 also fails open (that part IS documented). Consequence: a slow or crashed guard silently disarms on exactly the largest inputs. Never treat hook coverage as a boundary, and never pin a short `timeout` — the platform default is 600s, and the reverted attempt had pinned 10s against a parser that took 21s.  _(2026-07-25T00:00:00Z)_
- **[pitfall]** The lexer was QUADRATIC because bash rescans a string from its start for every `${var:offset:1}` — 32KB took 21s. `lex_char` reads through a bounded sliding window (`LEX_WINDOW`), which made it linear; `DM_GUARD_MAX_COMMAND` (64KB) refuses anything larger so the guard decides deterministically instead of racing a timeout it loses silently. Keep every new per-character scan on `lex_char`; a direct `${input:$i:1}` re-introduces the quadratic term.  _(2026-07-25T00:00:00Z)_
- **[invariant]** The guard classifies COMMAND POSITION vs ARGUMENT POSITION (#143): an option value is data, so a quoted sentence there is prose and is not re-entered. THREE rules stop that being a hole, and removing any one re-opens a verified smuggle — do not "simplify" them away: (1) a string whose own first word is `git` is classified wherever it sits (`entr -s "git reset --hard"`, `rsync -e "git push --force"`); (2) a bare shell/runner token in the ARGUMENTS makes the rest of the scan strict (`find . -exec sh -c "git push --force" \;` — `check_nested_shell` never fires there, because the shell is find's argument, not the segment's executable); (3) a command runner is strict from the start. What remains uncovered: an option value NOT starting with `git` on an unmodelled executable.  _(2026-07-25T00:00:00Z)_
- **[convention]** `restore`/`checkout` are CONDITIONAL, not refused (#89): `git restore <path>` and `git checkout [<tree-ish>] -- <path>` pass when every operand is a scoped literal path. `is_scoped_pathspec` tests per PATH COMPONENT — naming only `.`/`..` let `../..`, `./.`, `.//` and `src/../..` through, each a whole-worktree discard from one directory down. Absolute paths, globs and brace expansion are refused too. A named directory still discards its subtree; the test is lexical and does not stat.  _(2026-07-25T00:00:00Z)_
- **[pitfall]** The lexer models shell GRAMMAR nowhere, so keywords and heredocs each needed explicit handling: without `is_shell_keyword`, `for r in a b; do git -C "$r" status; done` made `do` the executable and refused ordinary compound shell; without the heredoc state, `--body "$(cat <<'EOF' … EOF)"` re-lexed prose as commands. `<<<` is a HERESTRING and must keep reaching `check_shell_input` — `bash <<< "..."` and `bash <<EOF` both stay refused.  _(2026-07-25T00:00:00Z)_
- **[pitfall]** Substitution content is captured by the LEXER in both plain and double-quoted state (#138) — scanning the raw string instead would wrongly classify `'$(...)'` inside single quotes, which no shell executes. Paren counting is quote-aware, and a genuinely unbalanced substitution is left opaque rather than denied: a real shell fails to parse it and runs nothing, so refusing it is pure over-blocking. The capture helpers set the global `SUBSTITUTION_END` rather than printing it — a command substitution would run them in a subshell and lose both the token text and the recorded command.  _(2026-07-25T00:00:00Z)_
